The user has a Windows 11 laptop and an iPhone 17. They watched Riley's YouTube video (8QPd6WD9Zzg) about Bluey, a blueberry focus companion. 4. The core problem: matching an encrypted protocol with no phone to test against

The Windows app must pair with an iPhone app that nobody could run during the build. Any one-byte difference in the handshake makes pairing fail with no useful error. The wire format, taken from the Swift source:

  • Bonjour service _googly._tcp. The TXT record bluey-id holds the first 12 bytes of SHA-256(secret) as 24 hex characters.
  • The server sends {"challenge": b64}. The client sends {"proof": b64}, where the proof is HMAC-SHA256(secret, "bluey-pair-v1" + challenge).
  • HKDF-SHA256 with the challenge as salt and the info strings bluey-v1-mac-to-phone and bluey-v1-phone-to-mac gives one key per direction.
  • Records use AES-GCM (nonce, ciphertext, tag), base64, one per line, with a strict sequence counter. The server's first sealed packet is {"command":"paired"}.
  • The QR text is bluey-pair: plus base64 of JSON {version:1, service, secret}.

Swift's Codable added three traps. Python tests pin all three:

  • Dates are seconds since 2001-01-01. The Python constant is _REFERENCE_DATE = 978307200.0.
  • UUIDs must be uppercase.
  • Every non-optional key must be present, or the decoder throws.

Without a phone, I built a scripted fake phone that speaks this protocol over real mDNS and ran the real Windows app against it, with a fake OpenAI server. That is the best evidence available, and it is not the same as a real iPhone. The README says so.

Lesson: with no real peer to test against, I wrote the peer's side from its source and pinned each encoding trap with a test.

6. What went wrong, and the fixes

Items 1 to 8 come from the compaction summary and are reconstructed. Items 9 to 14 come from the live transcript.

  1. Socket option. TransportSocket has no ioctl. Fix: setsockopt with SO_KEEPALIVE, TCP_KEEPIDLE 2, TCP_KEEPINTVL 1.
  2. Wrong coordinates at 125% scale. The code reported 1536x864 for a 1920x1080 panel, and the scale changed mid-run after importing uiautomation. Fix: set DPI awareness at control.py import and read DPI with GetDpiForMonitor. Near-miss: pointing looked slightly off at first. Without the DPI check the cause would have looked like an OCR error.
  3. Hotkey conflict. Ctrl+Alt+Space was taken on this laptop. Wake moved to Ctrl+Alt+W. Result: 7 of 7 hotkeys register.
  4. Idle CPU. Readings of 20.3% and 14.1% came from a busier test run. The tick now drops to 30 Hz when nothing is drawn. A clean idle measurement gave 2.2% of one core. Near-miss: the two high numbers were nearly accepted as the real figure.
  5. White text on white. The report card was unreadable in dark mode. Fix: explicit color: #17151F styles.
  6. Thread hop. A lambda connected to a signal did not guarantee a hop to the Qt thread. Fix: Dispatcher with a named @Slot and QueuedConnection.
  7. Hardening. Added a settings write lock, a focus ticker guard, an OSError guard in _persist, a TypeError catch in _parse_args, and a printed warning if capture exclusion is refused.
  8. Process handling. The venv python.exe is a launcher that starts a child process. The launcher PID is not the app PID, so stopping the launcher leaves the app running. Harnesses now exit by themselves. This also followed the rule: never kill a process by name.
  9. Input test never ran. The test waits for 20 idle seconds before it injects input. The laptop stayed active for 8 minutes. Output: you stayed active for 8 minutes: injection test not run, and the test is still open.
  10. QR "no usable data". The user scanned the QR code with the iPhone Camera app and saw "no usable data". This is expected: the QR text starts with bluey-pair:, which only the Bluey app reads, and Bluey was not installed on the phone yet.
  11. macOS runner SDK. The allowBluetoothHFP failure in section 5.3.
  12. Pages was already on. After the push, a pages-build-deployment run appeared. The Pages API showed source main, folder /, legacy build, public. I did not enable it and do not know what did. The whole branch was served at first. The user chose to serve only /docs, so the site root is now the docs/ folder.
  13. Automated security reviews. Four notes arrived from a review plugin. Three were about Windows/realtime.py, Mac/.../RealtimeHost.swift and Codex permissions. The fourth flagged macos-26 as an unknown runner label. I judged the label real (the run succeeded on a hosted runner) and said so. I did not change Mac/. The refused-shortcut check in Windows/realtime.py may miss Win-key aliases such as "windows" or "super". I have not verified that, and I asked before editing.
  14. Mermaid not rendered. I wrote four Mermaid diagrams and could not render them locally. They render on GitHub only. I told the user to check the repo page.

6a. Installing and pairing on the real iPhone (2026-11-05)

This part comes from the live transcript. It took about ten steps, and four of them hit a problem.

  1. My iTunes instruction was out of date. I told the user to download iTunes from apple.com, not the Microsoft Store. The screenshot showed apple.com/itunes/ redirecting to the Microsoft Store. I found Apple's direct link https://www.apple.com/itunes/download/win64. It returned a 301 to iTunes64Setup.exe (202,558,432 bytes). The file's signature was valid, signer Apple Inc.
  2. The silent iTunes install skipped the driver service. I ran iTunes64Setup.exe /quiet /norestart and it exited with 0. Windows then had no service "Apple Mobile Device Service" and no folder C:\Program Files\Common Files\Apple\Mobile Device Support. I extracted the bundle with /extract, checked that AppleMobileDeviceSupport64.msi (32.8 MB) was signed by Apple Inc., and installed it with msiexec /i ... /qn /norestart. The service then stayed in StartPending for more than 20 seconds, and I left it alone.
  3. The Sideloadly installer is unsigned. Get-AuthenticodeSignature returned NotSigned. I disclosed this, with the SHA-256 2E7D9A80BCD7912A9A2DAE1969645F8AF386AF46802A79303E727773B506362E, and the user chose to install. The first attempt failed with "The operation was canceled by the user", because the administrator prompt was not accepted. The second attempt worked.
  4. Sideloadly showed no device. The first screenshot read <no devices detected>. A Windows device query found the iPhone only over Bluetooth, not USB. After the user replugged the cable and tapped Trust, Windows listed Apple Mobile Device USB Composite Device and Sideloadly listed iPhone (27.2) ... @USB.
  5. Wrong Apple ID text. The Apple ID field held az9713, which is not an email. The user corrected it, and Sideloadly then reported [9 App IDs Remaining, updates 6d] and Done.
  6. Developer Mode confusion. The user did not see a Developer Mode question at first. The phone later restarted for it, which showed the install had worked. The user then could not find the app, so I read the IPA's Info.plist: display name Bluey, bundle ID co.visionairy.googly.phone, and no app icon, so iOS shows a plain icon.
  7. Windie was not running. No process matched bluey.py. I started it with pythonw bluey.py --pair (launcher PID 37828, app PID 13428).
  8. The camera closed as soon as it saw the QR code. The user thought this was a fault. The scan screen in iOS/Sources/QRPairingView.swift calls dismiss() as soon as link.pair(record) succeeds, so closing is the success path. A TCP connection from the phone on the local network to port 57251 of the PC confirmed the pairing.

Result: the user confirmed that Bluey's eyes track the mouse, and that Test a nudge shows a text bubble on the laptop. This is the first real-iPhone test. The Python code needed no change.

Fragility: the Windie mDNS socket showed ports on 127.0.0.1 and a VPN address, not on the Wi-Fi address. The phone connected anyway. If a later connection fails, turn off Tailscale first.

Known shortcuts

  • realtime.py sets engine attributes from the asyncio thread and relies on the GIL.
  • mDNS advertises every non-loopback IPv4 address, including a VPN address. If the phone finds the PC but cannot connect, check this first.
  • OCR needs an installed Windows language.
  • Codex voice jobs keep danger-full-access and no approvals, whatever the computer-control switch says. Riley's Mac code does the same, and the user has not reviewed it for Windows.

Scratch work that is gone after the session

These scripts lived in the session scratchpad and are not in the repository: smoke.py (drives the real App object), e2e_app.py and e2e_nudge.py (fake OpenAI and fake phone), exclusion.py, checks2.py, idle_cpu.py. To rebuild them: patch focus.API_BASE to a local HTTP server, set BLUEY_HOME to a temporary folder holding a fake keys.json, and call bluey.run_app().
