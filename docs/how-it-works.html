How Windie works: every component, explained

For a reader who knows software and networks, but not Apple signing, iTunes drivers, Sideloadly or CI. Written 2026-11-05, after the first real run on a Windows 11 laptop and an iPhone.

1. The short answer 2. The cast 3. End-to-end map 4. Why a Windows rewrite 5. GitHub Actions 6. Signing and Sideloadly 7. iTunes and the USB driver 8. Finding and pairing 9. How the mouse is tracked 10. The focus check 11. Every handoff 12. What broke 13. What is verified 14. Glossary

1. The short answer

The phone never sees your mouse. The Windows app (Windie) reads the cursor position on the laptop up to 60 times per second. It turns the position into two numbers, gazeX and gazeY, each between -1 and 1. It sends those numbers to the iPhone as a small encrypted message over your Wi-Fi. The iPhone app (Bluey) moves the pupils to match. Section 9 has an interactive version you can move your own mouse over.

Everything else on this page answers a different question: how did a Windows laptop get to talk to an iPhone app that Apple only lets you build on a Mac? There are two separate problems:

  1. Problem A: get the iPhone app onto the iPhone. You have no Mac. A cloud Mac builds the app (GitHub Actions). A Windows tool signs it with your Apple ID and installs it by USB (Sideloadly, helped by iTunes' USB driver).
  2. Problem B: make the two devices work together. The Windows app finds the phone on the Wi-Fi, proves it knows a shared secret from a QR code, and then sends encrypted messages.

4. Why Windie exists at all

Riley's Mac app calls Apple frameworks for everything that touches the computer: screenshots, text recognition, reading buttons, clicking, hotkeys, finding the phone, encryption and storing secrets. None of them exist on Windows. Windie replaces each one with a Windows equivalent, and keeps the phone protocol identical, byte for byte, so the iPhone app does not change.

How the Windows app is organised. Qt must own all windows on the main thread. All the logic (phone server, focus timer, OpenAI calls) runs in an asyncio loop on a second thread. A small Dispatcher hands work from one thread to the other. The Swift app gets this split from @MainActor.

Alternatives we rejected for the iPhone side. Expo Go runs JavaScript apps, and Bluey is native Swift, so it does not fit. TestFlight and the App Store need a paid Apple Developer account ($99 per year, from memory). Building on a borrowed Mac works, but you have no Mac. A rented Mac in the cloud was the cheapest path left.

5. Problem A, step 1: GitHub Actions builds the app on a rented Mac

What CI is

"CI" means continuous integration: a service runs a script on a fresh machine each time you push code. GitHub Actions is GitHub's version. The script is a YAML file in .github/workflows/. Each run starts a clean virtual machine (the "runner"), runs the steps, and throws the machine away. GitHub rents out Windows, Linux and macOS runners. The macOS runner is the only reason a user with no Mac can build an iPhone app.

What our workflow does

The file is .github/workflows/ios-ipa.yml. It starts when you click "Run workflow" (workflow_dispatch) or push to main with changes under iOS/, Shared/, project.yml or the workflow itself.

The workflow file (click to open) 
runs-on: macos-26
steps:
  - uses: actions/checkout@v4
  - run: brew install xcodegen
  - run: xcodegen generate
  - run: |
      xcodebuild -project GooglyEyes.xcodeproj -scheme GooglyEyes \
        -configuration Release -sdk iphoneos -derivedDataPath build \
        CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO \
        CODE_SIGN_IDENTITY="" DEVELOPMENT_TEAM="" build
  - run: |
      mkdir Payload
      cp -R build/Build/Products/Release-iphoneos/Bluey.app Payload/
      zip -r Bluey.ipa Payload
  - uses: actions/upload-artifact@v4
    with: { name: Bluey-ipa, path: Bluey.ipa }

Why "unsigned"?

The build has no access to your Apple ID or any certificate, so it turns signing off (CODE_SIGNING_ALLOWED=NO). Riley's project.yml names his Apple team (DEVELOPMENT_TEAM), and an empty value in the command overrides it. The result is a valid app that iOS will refuse to open. Signing happens later, on your PC (section 6).

The failure we hit here. The first run used macos-15 and stopped with iOS/Sources/LiveVoice.swift:487:97: error: ... has no member 'allowBluetoothHFP' and xcodebuild exit code 65. That Bluetooth option exists only in the iOS 26 SDK, and the macos-15 image has an older Xcode. Changing runs-on to macos-26 fixed it. Run 42060418575 succeeded and produced a 1,067,893-byte artifact named Bluey-ipa.

Cost: GitHub macOS minutes are free for public repositories and limited for private ones (from memory, not checked). This repository is public.

6. Problem A, step 2: signing, Apple ID and Sideloadly

Why iOS needs a signature

iOS runs only code that carries a signature chained to Apple. The signature must match a "provisioning profile", a document Apple issues that says "this developer may run this app on these specific devices". Normally the App Store, TestFlight or Xcode with a developer account gives you that. An unsigned .ipa has none of it, so the phone will not open the app.

What Sideloadly does

Sideloadly is a Windows/Mac program that does what Xcode does for a hobbyist. It logs into Apple with your Apple ID, asks Apple's developer service for a free development certificate, an App ID and a provisioning profile tied to your iPhone's ID, signs the .ipa with them, and installs the result over USB.

Limits of a free Apple ID. The signature lasts about 7 days. After that, Bluey stops opening, and you run Sideloadly again to renew it. A free account also limits how many apps you can sideload (3, from memory, not checked). A paid developer account ($99 per year, from memory) gives a one-year signature and TestFlight.

Sideloadly sends your Apple ID to Apple. The Sideloadly installer is unsigned (NotSigned), and it came from sideloadly.io. Use only the Sideloadly window for your password.

7. Problem A, step 3: iTunes and the USB driver

Why is a music program involved? An iPhone does not appear as a normal USB drive. A PC talks to it through Apple's own protocol, run by a small background service. Apple ships that service on Windows inside iTunes. Sideloadly asks the service three things: which phones are connected, can I pair with this one, and please install this app. Without the service, Sideloadly shows <no devices detected>.

The part we need is called Apple Mobile Device Support. It contains the driver and the service named Apple Mobile Device Service. (As far as I understand it, this service is Apple's version of the open-source usbmuxd. That is a general fact, not something I checked in the code.)

Three failures we hit here.

  1. apple.com/itunes/ now redirects to the Microsoft Store. Apple still serves the classic installer at https://www.apple.com/itunes/download/win64 (iTunes64Setup.exe, 202,558,432 bytes, signed by Apple Inc.).
  2. The silent install (/quiet) exited with 0 but left no "Apple Mobile Device Service" and no Mobile Device Support folder. The installer holds a second package inside. iTunes64Setup.exe /extract <folder> unpacked AppleMobileDeviceSupport64.msi (32.8 MB). Installing it with msiexec /i ... /qn fixed this. The service then sat in StartPending for more than 20 seconds before it worked.
  3. Windows listed the iPhone only over Bluetooth, not USB. A replug, an unlocked screen and a tap on "Trust" fixed it: Windows then showed Apple Mobile Device USB Composite Device.

Trust and Developer Mode, in one place

  • "Trust This Computer?" on the phone lets the PC talk to it over USB.
  • Settings, General, VPN & Device Management, your Apple ID, Trust lets the phone run apps signed by that Apple ID.
  • Developer Mode allows apps that did not come from the App Store. It needs a restart.
  • Local Network (an iOS permission) lets Bluey find the PC. Camera lets it scan the QR code.

8. Problem B: finding the PC and pairing

Finding

Both devices are on the same Wi-Fi. Windie announces a service called _googly._tcp using mDNS (the same idea as Apple's Bonjour). The announcement carries a TCP port (57251 in our run) and a short label, bluey-id, equal to the first 12 bytes of SHA-256 of the shared secret, written as 24 hex characters. The phone looks for that service name on the network and compares the label to the one it holds.

Pairing

The first time, the PC shows a QR code. It contains the text bluey-pair: plus base64 of a small JSON record with a version, the service name and a 256-bit secret. The phone scans it and saves the secret in its Keychain. From then on, every connection must prove it knows the secret, with no password typed and nothing sent in the clear.

Why the camera closes at once. The scan screen calls dismiss() the moment a valid code is saved (iOS/Sources/QRPairingView.swift). A fast close means success.

Protocol details (click to open)
  • Proof: HMAC-SHA256 of the secret over the text bluey-pair-v1 followed by the challenge.
  • Keys: HKDF-SHA256 with the challenge as salt. The info strings bluey-v1-mac-to-phone and bluey-v1-phone-to-mac give a different key for each direction.
  • Messages: AES-GCM (nonce, ciphertext, tag), base64, one per line, each wrapped as {"sequence": n, "packet": ...}. The sequence number must increase by one, so a recorded message cannot be replayed.
  • The Windows code is in Windows/link.py. It must match iOS/Sources/MacLink.swift and Shared/SecurePairing.swift exactly. Three Swift traps are pinned by tests: dates are seconds since 2001-01-01, UUIDs are uppercase, and every non-optional key must be present.

Why a Windows PC can pretend to be a Mac. The phone does not care what the other end is. It checks for the service name, the secret, and the message format. Windie speaks all three, so the phone treats it as the Mac app.

9. The mystery: how Bluey tracked a mouse on a different system

The phone is a screen that draws eyes. All the thinking happens on the PC. Every tick (about every 16 ms while something is drawn, about 33 ms when idle), Windie does this:

  1. Reads the cursor position with Qt's QCursor.pos(), which asks Windows for it.
  2. Treats the phone as sitting at a virtual point just below the bottom edge of the screen: horizontally at 20%, 50% or 80% of the screen width (the menu item "Phone Sits Under", default Center), vertically at 118% of the screen height.
  3. Computes the direction from that point to the cursor, as two numbers: 
    gazeX = clamp( (cursorX - phoneX) / (screenWidth * 0.5), -1, 1 )
gazeY = -max(0.15, min(1, (phoneY - cursorY) / (screenHeight * 1.1)))
  4. Sends {"face": {"gazeX": ..., "gazeY": ..., "mood": ..., "talk": ...}} to the phone, encrypted, over TCP.

The iPhone app moves the pupils toward those numbers with a spring (stiffness 260, damping 0.82 in FaceView.swift), which makes the motion smooth and adds a small jitter.

This is the full path of one eye movement, from your hand to the pupils. There are 12 hops. Two details are worth knowing. First, the phone works only from the latest target it received. If a packet is late, the pupils keep moving toward the older target, because of the spring. If none arrives for 2.5 seconds, the eyes wander on their own. Second, a packet carries no mouse position, no screen size and no timestamp that the phone uses for the eyes: only the numbers that hop 5 produced.

Why this works across two systems

QuestionAnswer
Where is the mouse read?On the PC only. The phone has no access to the PC's mouse.
What crosses the network?Two small numbers, a mood word and a talk level. About one short line of JSON per update, encrypted.
How often?Up to 60 times per second. Windie skips an update when both gaze values moved less than 0.004, and mood and talk did not change. It still resends once per second, so the phone knows the PC is alive (send_face in Windows/link.py).
How does the phone know where the PC screen is?It does not. It only receives a direction. The PC decides what "left" and "up" mean, using the virtual phone point.
Why do the eyes always look a little up?The virtual phone point is below the screen, so every cursor position is above it. The code limits gazeY to at least 0.15 upward.
Why did Bluey fall asleep in the video?In follow-mouse mode, if the mouse does not move for 5 seconds the mood becomes sleepy, and after 15 seconds resting (overlay.py).
How fast is it?I did not measure the delay between the cursor and the eyes. On a local network a small message should arrive in milliseconds. That is an expectation, not a measurement.

The "Test a nudge" button works the other way: the phone sends a command to the PC, and the PC shows a text bubble. That exercised the second direction of the same encrypted channel.

10. The focus check: screenshots and OpenAI

Mouse tracking needs no internet. The focus feature does. You tell Bluey a task. While the timer runs, Windie checks every 30 seconds (every 10 real seconds in Developer Mode):

  • Capture: one screenshot of the main display, using a Windows setting that hides Bluey's own windows from the capture.
  • Read: Windows OCR turns the screen text into words, and Windie records the front app name.
  • Decide: a reduced JPEG, the OCR text, the task and recent results go to OpenAI's Decisions API (gpt-6-luna), which answers on_task, off_task or uncertain.
  • Policy: a nudge needs several consecutive off-task answers over 120 to 240 seconds (40 to 80 focus seconds in Developer Mode).
  • Nudge: a second request (gpt-5.5) writes one gentle sentence. The PC shows it in a bubble. The phone chirps.

This path sends screenshots to OpenAI and costs money. It is the one part not yet tested with real OpenAI calls. The "Test a nudge" button skips the screenshot and OpenAI, which is why it was safe to test first.

13. What is verified and what is not

Verified

  • 35 unit tests pass.
  • The cloud build makes an .ipa.
  • Sideloadly installs it on a real iPhone.
  • The phone pairs by QR with Windie.
  • The eyes follow the mouse (video: demo page).
  • "Test a nudge" shows a bubble on the PC.
  • Windie's overlay does not appear in its own screenshots.

Not verified

  • Real OpenAI focus checks and nudges.
  • The chirp on the phone.
  • Hold-to-talk voice (the phone showed "Voice could not connect").
  • Clicking and typing into real windows.
  • A real Codex job.
  • The delay between the cursor and the eyes.
  • The 7-day, 3-app and free-minutes limits (from memory).
